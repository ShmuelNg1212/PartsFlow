### 2.1 Test strategy that follows from this

- **Database rules** (posting, reversal, idempotency, concurrency, RLS): Vitest runs the migrations against a scratch database in the local PostgreSQL. A small shim creates the Supabase objects that the migrations use: the `auth.users` table, `auth.uid()` (reads `request.jwt.claims`), the roles `anon`, `authenticated`, `service_role`, and a minimal `storage.objects` table. Each test sets `role authenticated` and the JWT claims, so RLS and grants apply as in Supabase.
- Concurrency tests open two real connections. One test makes two sales race for the same stock. One test makes two posts race for the same document. These tests can fail for the real reason.
- The shim is a test aid. It is not proof that Supabase behaves the same. Before a pilot, the same suite must run once against a real Supabase project (local or hosted).
- **Workflow tests** (Playwright, desktop and phone viewports) need real Supabase Auth, PostgREST, Storage, and Realtime. They need a Supabase project. See OPEN QUESTION Q1 in the plan.

## 4. Technical design findings

### 4.1 Data model

Tables (spec "Data and integrity"): `shops`, `memberships`, `products`, `counterparties`, `supplier_aliases`, `documents`, `document_lines`, `stock_movements`, `audit_events`. Two more are needed:

- `product_balances`: a cached balance per product (R-DATA-2). Only the posting and reversal functions write it, in the same transaction as the movements. A reconcile view compares it with `sum(stock_movements.qty)`.
- `post_attempts` is not needed. Idempotency comes from the document row itself: the post function locks the document row (`select … for update`) and returns the existing result when the status is already `posted`. A client idempotency key is stored on the document for the audit record.

Each shop-scoped table has `shop_id`. RLS allows a row when the user has a membership in that shop. The pilot has one shop, but `shop_id` keeps demo data separate (R-DEMO-1): demo data lives in a separate shop with `is_demo = true`, and the UI labels it.

### 4.2 Numbers

- Quantities: `numeric(14,3)`. Money: `numeric(14,2)` for prices, discounts, and totals. Unit conversion factor: `numeric(14,6)`, greater than 0.
- Base-unit quantity = confirmed quantity × conversion factor, rounded to 3 places in SQL. The client shows the same arithmetic with decimal.js. The server value is the truth.
- PostgREST returns `numeric` as JSON numbers by default. Large or precise values lose precision in JavaScript `number`. Cast to text in views and RPC return types, and parse with decimal.js.

### 4.3 Posting function (ADR 0001)

`post_document(p_document_id uuid, p_idempotency_key uuid, p_duplicate_override_reason text default null)`, `security definer`, `search_path` fixed.

1. Check the caller is an owner of the document's shop (R-ROLE-1).
2. Lock the document row. If status is `posted` and the key matches, return the stored result (R-POST-6). If status is `posted` with another key, return the same result with "already posted". If status is not `draft`, raise.
3. Validate each line: product selected (R-DOC-6), quantity greater than 0, conversion factor present when the unit differs from the base unit (R-POST-11), received quantity confirmed for receipts (R-POST-3).
4. Check duplicates (R-POST-9): another posted document with the same number + counterparty + direction, or the same file hash. Without an override reason, raise. An override needs the owner role and a reason, and writes an audit event.
5. Lock the affected `product_balances` rows in product-id order (avoids deadlocks). For a sale, check each balance ≥ requested quantity. On failure, raise with product, on-hand quantity, and requested quantity (R-POST-8). Row locks make concurrent sales serialize, so they cannot oversell (R-POST-7).
6. Insert movements, update balances, set status `posted`, `posted_at`, `posted_by`, write the audit event. All in the function's transaction (R-POST-5).

`reverse_document(p_document_id, p_reason)` follows the same pattern: owner only, posted → reversed, compensating movements linked by `reverses_movement_id`, blocked when a balance would go negative (D5).

Clients get no `insert/update/delete` grant on `stock_movements`, `product_balances`, `audit_events`. A trigger on `documents` rejects any change of `status` to `posted` or `reversed` unless a transaction-local flag that only the functions set is present, and rejects any edit of a non-draft document or its lines (R-DATA-7, R-POST-10).

### 4.4 Product changes and opening quantities

- Products are written through RLS by owners only. Opening quantity uses `set_opening_quantity(product_id, qty)`: owner only, allowed only when the product has no movements yet. It writes a movement with source `opening` (R-PROD-3).
- CSV import: the client parses and validates the file and shows a preview (R-PROD-2). The commit calls `import_products(jsonb)`, which validates again on the server and writes products and opening movements in one transaction.

### 4.5 Matching (R-DOC-6, R-PROD-5)

- Candidates come from an RPC `suggest_products(shop, counterparty, description, part_number)`. Order: confirmed supplier alias (exact), exact normalized part number, then trigram similarity on description.
- A suggestion is "confident" only when exactly one candidate comes from an alias or an exact part number + brand match. Every other case is ambiguous. The line stays "needs review" until a user selects a product.
- Part number normalization removes spaces, dashes, and dots and uses upper case, only for comparison. Two products with the same normalized part number and different brands are both shown, and neither is auto-selected.
- A posted line with a confirmed product saves or confirms a supplier alias (R-DOC-8). The post function writes the alias, so drafts never create aliases.

### 4.6 Files and extraction (ADR 0002)

- Bucket `documents`, private. Object path `{shop_id}/{document_id}/{filename}`. Storage RLS allows read and insert only to members of that shop. No update or delete for clients (R-DOC-1).
- Edge Function `extract-document`: verifies the caller's JWT and membership, downloads the file with the service role, computes SHA-256 and writes `file_sha256`, then calls the selected extractor and writes raw values only (`raw_*` columns or a `raw` jsonb per line). It never touches stock.
- Extractor interface: `extract(file: Uint8Array, mime: string) → ExtractionResult` with per-field value and confidence. The demo provider matches the SHA-256 of bundled synthetic samples only. The original hosted OCR adapter was later removed under ADR 0005.
- The initial hosted provider was not evaluated. The current provider decision is in ADR 0005. No accuracy result was claimed.

### 4.7 Realtime (R-STOCK-3)

Supabase Realtime `postgres_changes` on `product_balances` and `documents`, filtered by `shop_id`. On an event, the client invalidates the related TanStack Query keys. Realtime respects RLS for `postgres_changes`.

### 4.8 Offline and connection state

- A banner shows when `navigator.onLine` is false or a request fails with a network error.
- The draft form saves to the server on demand and keeps an unsaved copy in `localStorage` per document. On reload, the app offers to restore it.
- The post button shows "Posting…" until the RPC returns. The UI shows "Posted" only from the server response (R-UI-1). A network failure during post shows "Result unknown. Check status" and refetches the document. A retry with the same idempotency key is safe.

## 5. Visual direction (minimalist-ui, adapted for an app)

The skill targets editorial pages. PartsFlow is a work tool, so these rules apply with the adaptations below.

**Keep:**
- Warm monochrome. Canvas `#FBFBFA`, surfaces `#FFFFFF`, borders `#EAEAEA`, text `#2F3437`, secondary text `#787774`.
- Color only for meaning, as muted pastels: red `#FDEBEC`/`#9F2F2D` (blocked, error, insufficient stock), yellow `#FBF3DB`/`#956400` (needs review, uncertain field, low stock), green `#EDF3EC`/`#346538` (posted, success), blue `#E1F3FE`/`#1F6C9F` (information, demo label).
- Primary button `#111111` on white text, radius 6px, no shadow, `scale(0.98)` on active.
- Cards and panels: 1px `#EAEAEA` border, radius 8px. No heavy shadows. No gradients.
- Status badges: small, uppercase, wide tracking, pastel background.
- Fonts: Geist Sans for UI, Geist Mono for SKUs, part numbers, quantities, and money (tabular figures). An editorial serif (Newsreader) only for page titles. No Inter or Roboto.
- Icons: Phosphor (regular or bold weight), one weight across the app. shadcn/ui defaults to Lucide; replace its icons.
- `<kbd>` for keyboard shortcuts (for example the save shortcut in the workspace).
- Plain, specific copy. No marketing words.

**Change for an app:**
- No scroll-entry animations, staggered reveals, ambient blobs, background images, or "macro-whitespace" (`py-24`). Data screens need density and stability. Motion is limited to short state feedback (150–200 ms opacity/transform) and respects `prefers-reduced-motion`.
- Width: the invoice workspace uses the full width (document beside table). Text pages keep a readable maximum width.
- Touch targets at least 44×44 px on phones. Inputs use 16 px text on phones (no iOS zoom).

**Ban list for the design check at rendezvous:** Inter/Roboto/Open Sans, Lucide icons, `shadow-md` and stronger, gradients, large saturated color areas, pill-shaped cards or primary buttons, emojis, placeholder names (John Doe, Acme), marketing clichés, decorative charts.

## 6. Risks

1. No Supabase project exists yet. Without one, the app cannot run end to end and Playwright cannot run (Q1).
2. The database test shim can differ from real Supabase in grants and RLS details. Mitigation: run the suite against real Supabase before the pilot.
3. New major versions (React Router 8, TypeScript 7, Vite 8, Vitest 5) can have ecosystem gaps. Mitigation: read docs; pin back one major where a plugin is not ready, and record the reason.
4. Extraction quality is unknown. The pilot must not depend on it: manual entry is the first complete path.
