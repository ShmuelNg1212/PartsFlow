# Hosted PaddleOCR scanner

Date: 2026-10-18. Mode: technical.
Skills: research, codebase-design.

## Goal

The live site must read uploaded invoices with PaddleOCR. Today the live `extract-document` function uses the labelled demo extractor. The PaddleOCR worker runs only on the developer's Mac, on loopback. The live site cannot reach it.

## Current foundation

- `ocr/worker.py` is a small HTTP server. It has `/health` and `/read`. It needs a bearer token of 32 or more characters. It reads one document at a time and answers 503 when busy. It refuses a non-loopback bind address. It holds no Supabase credential.
- `ocr/reader.py` pins the models (`PP-OCRv6_medium_det`, `PP-OCRv6_medium_rec`, and two orientation models). It runs on CPU. It limits bytes (10 MB), pages (5), and pixels (40 MP).
- `supabase/functions/_shared/extraction/paddle.ts` holds `workerReader` (HTTP client with a timeout) and `localPaddleExtractor` (maps text lines to invoice fields). It has no Deno or npm imports. The Edge Function can import it without change.
- `supabase/functions/extract-document/index.ts` builds `demoExtractor()` unconditionally. `handler.ts` already does the access checks, the hash, the failure fallback, and the `apply_extraction` write. The extractor is the only seam that must change.
- The provider label is the constant `paddleocr-local`. Failure messages say "The local scanner is not running." Both are wrong for a hosted scanner.

## Measured runtime facts

From [the extraction plan](../plan/1792314680_real_invoice_extraction.md) and [setup](../wiki/setup.md), on the developer's ARM64 Mac:

- Peak resident memory: about 4.8 GB.
- One page: about 7 to 11 s on CPU.
- Pipeline load from a warm model cache: 2.5 s. With model downloads: 68 to 100 s.

These numbers are not measured on Linux x86-64. A container needs its own measurement.

## Platform limits

Supabase Edge Functions: wall clock 150 s on Free, 400 s on paid plans. Request idle timeout 150 s. CPU time 2 s. Waiting on `fetch` does not use CPU time. A cold scanner start plus one read must finish inside 150 s. Source: [limits](https://supabase.com/docs/guides/functions/limits).

Both Supabase projects are on Free in `ap-southeast-1` (Singapore).

## Hosting options

| Option | Cost at pilot volume | Region | Operations | Cold start |
|---|---|---|---|---|
| A. Google Cloud Run, scale to zero | Probably inside the monthly free tier (see below). Needs a billing account. | `asia-southeast1` (Singapore) | Managed HTTPS. No server patching. Remote image build. | Yes. Not measured. |
| B. Hetzner cloud server, always on | CX43 (16 GB) €15.99/month in Germany or Finland. In Singapore only CPX32 €48.99/month is listed. Excl. VAT and IPv4. | Germany/Finland, or Singapore at higher cost | We patch the OS, run TLS (for example Caddy), and restart on failure. | No |
| C. Fly.io Machine, auto stop | shared-cpu-8x with 8 GB about $47/month if always on (Ashburn price). Less with auto stop. | `sin` available; price differs per region | Managed HTTPS. Machine config. | Yes |
| D. Developer's Mac with a tunnel | $0 | Wherever the Mac is | Works only while the Mac is on and awake. | No |

Sources: [Cloud Run pricing](https://cloud.google.com/run/pricing), [Cloud Run memory limits](https://docs.cloud.google.com/run/docs/configuring/services/memory-limits), [Hetzner price adjustment, 15 June 2026](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/), [Fly.io pricing](https://fly.io/docs/about/pricing/).

### Cloud Run cost estimate

Request-based billing (Tier 1 rates): $0.000024 per vCPU-second, $0.0000025 per GiB-second. Free each month: 180,000 vCPU-seconds, 360,000 GiB-seconds, 2 million requests. Tier 2 regions have higher rates and smaller free amounts. This study did not confirm the tier of `asia-southeast1`.

8 GiB needs at least 2 vCPU. Assume 4 vCPU and 8 GiB, and 30 s billed per document including a cold start. 600 documents a month then use 72,000 vCPU-seconds and 144,000 GiB-seconds. That is inside the Tier 1 free amounts and probably inside Tier 2 free amounts. This is an estimate, not a measurement. A max-instances limit caps the worst case.

Idle instances that are not minimum instances are not charged under request-based billing.

### Recommendation

Option A. Reasons:

- The region is the same as Supabase. Invoices stay in Singapore.
- The expected cost is near zero at pilot volume. A max-instances limit caps cost.
- HTTPS and restarts are managed. There is no server to patch.
- Cloud Build builds the image remotely. This Mac has no Docker. Cloud Run needs x86-64 Linux images by default; a remote build avoids cross-builds on ARM64.

Risks of A:

- Cold start time is not known. It includes the image pull and model load. If cold start plus read exceeds the Edge Function budget, the user sees "enter the lines by hand". Mitigation: put the models in the image, and measure. A minimum of one instance removes cold starts but costs money all month.
- A Google Cloud account with billing is needed. Only the human can create it.

Option B is the fallback if cold starts are too slow and an always-on cost is acceptable.

## Required code changes

1. **Worker bind.** Cloud Run sends traffic to `0.0.0.0:$PORT`. Keep loopback as the default. Allow a non-loopback bind only when an explicit hosted setting is present, and only with a token. Keep the 32-character minimum.
2. **Container.** Add `ocr/Dockerfile`. Use Python 3.11 and the locked `uv.lock`. Download the pinned models at build time, so a cold start loads from disk. Run as a non-root user.
3. **Extractor choice.** The Edge Function selects the PaddleOCR extractor only when both `OCR_WORKER_URL` (HTTPS) and `OCR_WORKER_TOKEN` are set. Otherwise it keeps the demo extractor. Put this choice in a small pure function so Vitest can test it.
4. **Labels and messages.** Pass the provider label and the "not available" text into the extractor. Hosted label: `paddleocr`. Local label stays `paddleocr-local`. Hosted message: "The scanner is not available now. Enter the lines by hand."
5. **Timeout.** The worker call in the Edge Function must end before 150 s. Use 120 s. The handler already turns a failure into a draft with no lines.
6. **Concurrency.** Set Cloud Run concurrency to 1. The worker already reads one file at a time. Set max instances to a small number, for example 2.

No migration is needed. No frontend change is needed beyond the provider label shown in the banner, if the banner shows it.

## Security and privacy

- Invoice bytes leave Supabase and go to Google Cloud Run in Singapore. This is a new data processor. It needs an ADR and human approval. Real invoices need shop consent (R-EXT-2).
- The worker stores nothing. It logs method and path only. Keep this.
- The Cloud Run URL is public. The bearer token is the only gate. Store it as a Supabase function secret and a Cloud Run secret. Never put it in the frontend.
- The Edge Function keeps all access checks. The worker never sees a user token or a shop ID.
- `OCR_WORKER_URL` must be HTTPS in the hosted function. Refuse plain HTTP.
- OCR text stays untrusted data. The mapper already treats it as data.

## Rollback

Unset `OCR_WORKER_URL` on the Edge Function. The function returns to the demo extractor. Delete or scale the Cloud Run service to stop cost.
